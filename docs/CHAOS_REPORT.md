## 2. Методика

### 2.1 Сценарий 1 — офлайн (критерий готовности из дорожной карты)

1. Чистый каталог; сервер запущен (`--memtable-mb 2 --sync strict`, scrubber выключен).
2. Вставлено 100 000 ключей `chr1:NNNNNNNN` с псевдослучайными «геномными»
   значениями (8 байт каждое), отправлен CHECKPOINT — все ключи в .sst-сегментах.
3. Сервер убит сигналом **SIGKILL** (семантика сбоя, а не graceful).
4. **White-box порча**: тест читает суперблок каждого .sst (геометрия k, m,
   число страйпов), восстанавливает интерливинг и выбирает 80 секторов 4 KiB
   с ограничением **≤ m=2 повреждённых шардов на страйп** — зона гарантии RS.
   Чередуются режимы: bit-flip (64 XOR-байта в секторе) и zero-fill (полный
   ноль = мёртвый сектор).
5. `dna-db-core doctor --data-dir … --fix --json` — офлайн-скан и ремонт.
6. Рестарт сервера; чтение **всех** 100 000 ключей и сверка с эталоном.

### 2.2 Сценарий 2 — live (порча на работающем сервере)

Тот же профиль порчи выполняется **при работающем сервере**. Затем читаются
все 100 000 ключей: каждый промах CRC невидимо для клиента чинится on-read
repair (реконструкция из parity + перезапись + журнал) до возврата значения.

### 2.3 Сценарий 3 — over-damage (за границей гарантии)

В крупнейшем сегменте обнуляются 4 дата-шарда ОДНОГО страйпа (m=2 → страйп
потерян математически). Проверяется честность:

- `doctor` обязан выдать вердикт **UNREPAIRABLE** с числом непоправимых страйпов;
- `doctor --fix` не должен «починить» потерянное;
- после рестарта движок работает: ключи потерянного страйпа возвращают
  ошибку с локализацией (карантин), **ни одно** доступное значение не искажено.

## 3. Результаты и наблюдения

| Метрика | Значение |
|---|---|
| Загрузка 100k ключей (strict fsync) | 2.4 с (~41 000 ops/s) |
| Doctor scan+fix 80 бляшек | 0.1 с (≈ 3.2 MB/s полной проверки, ремонт из parity — миллисекунды на страйп) |
| Полная верификация 100k ключей | 2.7–2.9 с (~35 000 reads/s) |
| Блоков переписано из parity (сценарий 1) | 80 из 80 (100 %) |
| Повреждений, устранённых on-read (сценарий 2) | 57, пропусков/искажений — 0 |
| Ключей в карантине (сценарий 3) | 483 (только потерянный страйп ≈ 16 KiB данных × записи/блок) |

Выводы:

- **Гарантия подтверждена**: ≤ m=2 шарда на страйп → 100 % восстановление и в
  офлайне (doctor), и на живом сервере (on-read).
- **Интерливинг работает**: 80 секторов, разбросанных по файлу, никогда не
  убивают страйп (иначе сценарий 1 упал бы — план порчи это отслеживает).
- **Честность подтверждена**: за границей гарантии система не молчит и не
  врёт — вердикт UNREPAIRABLE, карантин, 0 неверных значений.
- Накладные расходы RS-кодирования на запись — см. `docs/BENCHMARKS.md` §v3.0.

## 5. Честные ограничения испытания

- Порча выполняется процессом теста через обычный `write()` — это модель
  bit-rot/битых секторов на уровне содержимого, а не реальной деградации
  железа. Модель совпадает с описанной в дорожной карте (§1, решение 2).
- План порчи сценария 1/2 соблюдает `≤ m` шардов на страйп (зона гарантии);
  за границей гарантии отвечает сценарий 3.
- Файловая система песочницы — overlayfs; сегменты ~1–4 МБ. На NVMe с
  большими файлами абсолютные тайминги изменятся, вердикты — нет.
- WAL в сценариях не повреждался (его защита — CRC кадров + зеркало;
  RS-parity закрытых WAL-сегментов покрыта unit-тестами `wal::tests`).
