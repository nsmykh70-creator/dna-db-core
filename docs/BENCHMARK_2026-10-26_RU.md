# DNA-DB vs MySQL vs PostgreSQL vs Oracle: измеренные пределы и насыщение

**Дата:** 2026-10-26  
**Стенд:** DESKTOP-3OOBQQD, Windows 11 (10.0.26200), 6 CPU, ~15,86 GB RAM  
**Клиент:** Python 3.12.9, один процесс-нагрузчик  
**DNA-DB:** `dna-db-core 3.3.0`, release-сборка, `--sync strict`, self-signed TLS, XChaCha20-Poly1305 at-rest. Фиксированная нагрузка снята на v3.3.0; прогон 1 млн строк — на hot path v3.2.0 (изменения v3.3.0 — mTLS/rotation/vendored codec, не storage-write path).  
**MySQL:** 8.4.11 в Docker Desktop/WSL2, `innodb_flush_log_at_trx_commit=1`  
**PostgreSQL:** 17.11 в Docker Desktop/WSL2, `synchronous_commit=on`  
**Oracle:** Oracle Database 23ai Free в Docker, thin-клиент `oracledb 26.0.1`  
**Повторяемость:** скрипты `scripts/bench_compare.py`, `scripts/bench_max.py`; JSON-результаты и логи сохранены в `C:\dnadb`.

> Это **не** сравнение «одинакового железа под одинаковой ОС»: DNA-DB работает нативно в Windows, MySQL/PostgreSQL/Oracle — в Docker Desktop/WSL2. Контейнеры добавляют сетевой и filesystem-оверхед. Все системы использовались с durability-on настройками; цифры показывают поведение на этом стенде, а не универсальный рейтинг СУБД.

## 1. Что именно измерялось

### 1.1. Фиксированная смешанная нагрузка

Одинаковый набор из `bench_compare.py`:

| Параметр | Значение |
|---|---:|
| Последовательная запись | 20 000 строк |
| Многопоточная запись | 16 000 строк × 8 потоков |
| Пакетная запись | 16 000 строк, batch=200 |
| Точечное чтение | 8 000 операций |
| Смешанный режим | 8 потоков × 1 000 операций, 80% чтение / 20% запись |
| SQL-загрузка | 5 000 строк |
| SQL SELECT по PK | 3 000 запросов |
| Размер значения | 160 байт (`ACTG` × 40) |

DNA-DB измерена в двух режимах:

- **production:** TLS + at-rest AEAD (XChaCha20-Poly1305);
- **legacy:** `--no-tls --no-encryption`, только как baseline для выделения overhead.

Дополнительно сняты **TLS-only** и **AEAD-only**, чтобы не смешивать два разных оверхеда.

### 1.2. Насыщение и объём

`bench_max.py`:

- загрузка **1 000 000 строк** по 160 байт через SQL batch=200;
- точечный `SELECT ... WHERE pk = ?`;
- `UPDATE` по PK;
- 1, 2, 4, 8, 16, 32 клиентских соединения;
- по 1 000 SELECT и 100 UPDATE на клиента;
- проверка количества строк после загрузки;
- измерение занятого места: `DATA` для DNA-DB, `information_schema` для MySQL, `pg_total_relation_size` для PostgreSQL, `user_segments` для Oracle.

**Важно:** 32 клиента — верхняя точка этого прогона, а не найденная точка падения. Ни одна система не вернула ошибку и не упала; на 32 клиентах latency ещё растёт, а throughput у DNA-DB/PostgreSQL продолжает расти. Поэтому ниже приведён **лучший измеренный результат**, а не «теоретический максимум СУБД».

## 2. Фиксированная нагрузка: production DNA-DB против MySQL/PostgreSQL

| Система | load, 1/s | load-mt, rows/s | batch, rows/s | point read, ops/s | mixed, ops/s | SQL load, /s | SQL SELECT, /s |
|---|---:|---:|---:|---:|---:|---:|---:|
| **DNA-DB TLS+AEAD** | **1 004** | 1 087 | 32 942 | **3 771** | 3 786 | **840** | **3 491** |
| DNA-DB legacy | 1 064 | 1 124 | **64 496** | 5 310 | **4 078** | 906 | 3 626 |
| MySQL 8.4 | 153 | 690 | 14 530 | 664 | 3 156 | 150 | 670 |
| PostgreSQL 17 | 406 | **1 986** | 42 712 | 794 | 3 571 | 422 | 759 |

Отношение production DNA-DB к конкурентам:

| Метрика | К MySQL | К PostgreSQL |
|---|---:|---:|
| Последовательная запись | **×6,6** | **×2,5** |
| Многопоточная запись | **×1,6** | ×0,57 |
| Пакетная запись | **×2,4** | ×0,82 |
| Точечное чтение | **×5,4** | **×4,5** |
| Смешанный режим | **×1,13** | ×1,00 |
| SQL-загрузка | **×6,2** | **×2,2** |
| SQL SELECT по PK | **×5,0** | **×4,4** |

**Интерпретация:** на этой нагрузке DNA-DB быстрее в точечных чтениях и одиночных fsync-записях. PostgreSQL быстрее в многопоточной вставке; на пакетной вставке DNA-DB с TLS+AEAD проигрывает PostgreSQL примерно на 18%. Смешанный режим у DNA-DB и PostgreSQL практически одинаковый.

### 2.1. Цена production-hardening

Один и тот же стенд, одна и та же нагрузка:

| Режим DNA-DB | load | batch | point read | mixed | SQL SELECT |
|---|---:|---:|---:|---:|---:|
| legacy (no TLS, no AEAD) | 1 064 | 64 496 | 5 310 | 4 078 | 3 626 |
| TLS only | 1 008 | 73 174 | 4 609 | 4 295 | 3 418 |
| AEAD only | 1 052 | 33 611 | 4 171 | 3 902 | 3 426 |
| **TLS + AEAD** | **1 004** | **32 942** | **3 771** | **3 786** | **3 491** |

Снижение относительно legacy:

- sequential load: **−5,6%**;
- batch: **−48,9%**;
- point read: **−29,0%**;
- mixed: **−7,2%**;
- SQL SELECT: **−3,7%**.

Основной вклад в падение batch даёт AEAD на каждое значение: 16 000 строк × 160 байт — это 16 000 аутентифицированных конвертов, а batch-фаза состоит всего из 80 сетевых обменов, поэтому стоимость crypto видна особенно сильно. Для чтений TLS и AEAD дают примерно сопоставимый вклад. Это реальная цена, её нельзя «спрятать» в отчёте.

## 3. Насыщение на 1 000 000 строк

| Система | Загрузка, rows/s | Время загрузки | SELECT, ops/s (клиенты) | UPDATE, ops/s (клиенты) | Занято, MiB | Байт/строку |
|---|---:|---:|---:|---:|---:|---:|
| **DNA-DB TLS+AEAD** | 3 019 | 331 с | **6 876** (32) | 1 060 (32) | 750,2 | 786,7 |
| DNA-DB legacy | 3 324 | 301 с | 7 628 (32) | 1 059 (16) | 647,3 | 678,7 |
| MySQL 8.4 | 3 003 | 333 с | 3 183 (16) | 1 134 (32) | 174,7 | 183,2 |
| PostgreSQL 17 | **6 293** | 159 с | 5 750 (32) | **3 341** (32) | 212,9 | 223,2 |
| Oracle 23ai Free | 1 494 | 669 с | 4 306 (16) | 2 500 (32) | 208,0 | 218,1 |

Все прогоны: `verified=True`, `errors=0`. При 32 клиентах:

- DNA-DB production: SELECT p50 2,95 мс / p99 9,55 мс; UPDATE p50 18,93 мс / p99 28,68 мс;
- PostgreSQL: SELECT p50 4,93 мс; UPDATE p50 8,78 мс;
- MySQL: SELECT p50 8,43 мс / p99 22,5 мс; UPDATE p50 11,2 мс / p99 64,3 мс;
- Oracle: SELECT p50 6,24 мс; UPDATE p50 8,07 мс.

### 3.1. Где начинает «падать»

В этом прогоне **точки падения не найдено**: ошибок не было ни на одной системе, вплоть до 32 клиентов. Наблюдаемые признаки приближения к пределу:

- MySQL: SELECT достиг максимума на 16 клиентах (3 183 ops/s), на 32 — 3 140 ops/s, p99 вырос до 22,5 мс;
- Oracle: SELECT достиг максимума на 16 клиентах (4 306 ops/s), на 32 — 4 205 ops/s;
- DNA-DB и PostgreSQL на 32 клиентах ещё росли; для поиска плато нужен отдельный прогон на 64/128 клиентов и более длительный soak.

Поэтому корректная формулировка: **«измеренный максимум на этом стенде — 6 876 SELECT/s и 1 060 UPDATE/s у DNA-DB; отказ не наблюдался»**, а не «DNA-DB выдерживает ровно столько запросов».

### 3.2. Почему DNA-DB занимает больше места

DNA-DB хранит не одну копию значения, а dual-strand/parity-представление для self-healing. На 1 млн строк по 160 байт:

- логический payload: ~160 MB;
- MySQL: 175 MiB;
- PostgreSQL: 213 MiB;
- Oracle: 208 MiB;
- DNA-DB production: 750 MiB (786,7 байт/строку).

Это осознанный trade-off: примерно 3,5× пространства против MySQL за возможность восстановления повреждённых сегментов. При планировании ёмкости нужно умножать полезный объём на этот коэффициент, а не считать 160 байт на строку.

## 4. Теоретические лимиты и измеренный объём

| СУБД | Теоретический предел БД | Предел объекта/записи | Измерено на стенде |
|---|---|---|---:|
| **DNA-DB** | Нет жёсткого общего лимита; ограничен диском и u64-идентификаторами сегментов | TCP-кадр 16 MiB; ключ ≤64 KiB; внутренняя запись сегмента ≤64 MiB | 1 000 000 строк / 750 MiB |
| **PostgreSQL 17** | Практически без лимита (диск) | Таблица до 32 TB; поле до 1 GB; строка до 1,6 TB | 1 000 000 строк / 213 MiB |
| **MySQL 8.4 InnoDB** | Практически без лимита (диск) | Табличное пространство/таблица до 64 TB; LOB до 4 GB | 1 000 000 строк / 175 MiB |
| **Oracle 23ai Free** | Ограничена редакцией: 12 GB пользовательских данных | Bigfile tablespace до 128 TB (EE); LOB до 4 GB | 1 000 000 строк / 208 MiB |

Пояснения:

- «Теоретический предел» — документированный лимит СУБД, а не обещание, что конкретный сервер выдержит такой объём при данной RAM/CPU/ФС.
- 1 млн строк — **проверенный** объём, а не максимум. Для DNA-DB рост ёмкости линеен по диску с оговоркой на compaction и паразитные копии; для PostgreSQL/MySQL/Oracle ограничение упирается в диск, обслуживание и бэкапы.
- Oracle Free в контейнере имеет лицензионный лимит 12 GB user data; это не предел Oracle Enterprise Edition. Для полноценного сравнения Oracle EE нужен отдельный стенд и лицензия.
- DNA-DB не имеет отдельного «max database size»; ограничение задаётся файловой системой, диском и 64-битными счётчиками. Но это не значит, что 1 TB данных будет удобно обслуживать: offline-операции и key rotation требуют свободного места и RAM.

## 5. Выводы

1. **Production TLS+AEAD не убивает производительность, но заметно меняет профиль.** Sequential load теряет ~8%, point read ~27%, batch ~55%. Для batch-нагрузок нужно либо увеличивать размер транзакции, либо принимать стоимость AEAD.
2. **На точечных чтениях и одиночных записях DNA-DB быстрее MySQL/PostgreSQL на этом стенде** — за счёт native Windows, LSM и более короткого пути запроса. Это преимущество нельзя автоматически переносить на все workloads.
3. **PostgreSQL лучше держит многопоточную запись и пакетную загрузку**, особенно на 1 млн строк: 6 293 rows/s против 3 019 у DNA-DB TLS+AEAD.
4. **На 1 млн строк ни одна система не отказала до 32 клиентов.** Насыщение MySQL/Oracle по SELECT наступило на 16 клиентах; DNA-DB/PostgreSQL ещё не вышли на плато.
5. **Цена self-healing — место.** DNA-DB занимает ~3,5× больше MySQL на том же логическом наборе. Это нужно учитывать в capacity planning.
6. **Oracle Free пригоден для функционального сравнения, но не для честного сравнения цены/масштаба**: 12 GB user data и ограниченные ресурсы контейнера.
