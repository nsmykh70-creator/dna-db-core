# DNA-DB Wire Protocol v2.1

Транспорт: TCP. Каждый кадр = `[length u32 LE][payload]`.
`length <= MAX_FRAME_SIZE = 16 777 216` (16 MiB). Нарушение → соединение закрывается.

Все операции, кроме `AUTH`, требуют предварительной аутентификации в рамках соединения.

## Опкоды

| Опкод | Имя | Payload | Ответ |
|---|---|---|---|
| `0x00` | PING/STATUS | пусто | framed: JSON `{"status":"ok","auth":bool,"stats":"...","segments":N}` |
| `0x01` | AUTH | `user:pass` (UTF-8) | raw 2 байта: `OK` или `NO`; после 5 неудач с одного IP — framed `ERR: IP temporarily locked...` и разрыв |
| `0x02` | GET | key (сырые байты) | framed: value; если ключа нет — framed длины 0 |
| `0x03` | PUT | `[klen u16 LE][key][value]` | raw `OK` или framed `ERR: ...` |
| `0x04` | DELETE | key | raw `OK` или framed `ERR: ...` |
| `0x10` | DNAQL | текст запроса (UTF-8) | framed JSON: `{"ast":"...","rows":[{...}],"note":"...","time_us":N}` или `ERR: ...` |
| `0x11` | SQL | текст запроса (UTF-8) | framed JSON: `{"columns":[...],"rows":[{...}],"plan":"...","time_us":N}` или `ERR: ...` |
| `0x12` | CHECKPOINT | пусто | raw `OK` — flush + усечение WAL |

## Гарантии

- `PUT` подтверждается `OK` **после** fsync кадра WAL (в режиме `--sync strict`). Сбой процесса между `OK` и ответом клиенту оставляет запись durable.
- `GET` читает active memtable → immutable memtable → сегменты (новые→старые); tombstone эквивалентен отсутствию.
- `CHECKPOINT` синхронен: после `OK` весь объём данных лежит в SSTable-сегментах, WAL пуст.

## Совместимость

`scripts/kill9_test.py` использует ровно этот протокол:
`AUTH (0x01 admin:password) → OK`, `PUT (0x03 + klen u16 + key + value) → OK`,
`GET (0x02 + key) → [len u32][value]`. Тест запускает сервер как
`dna-db-core serve --data-dir <dir> --port <port>`.

## Пример клиента (Python)

```python
import socket

def frame(p): return len(p).to_bytes(4, 'little') + p
def recv_frame(s):
    n = int.from_bytes(s.recv(4), 'little')
    return s.recv(n) if n else b''

s = socket.create_connection(("127.0.0.1", 9999))
s.sendall(frame(b"\x01admin:password")); assert s.recv(2) == b"OK"

# PUT
payload = b"\x03" + (3).to_bytes(2, 'little') + b"chr" + b"ATGC"
s.sendall(frame(payload)); assert s.recv(2) == b"OK"

# GET
s.sendall(frame(b"\x02chr")); v = recv_frame(s)   # b"ATGC"

# DnaQL
s.sendall(frame("\x10chr ? 'ATGC' ~0".encode())); print(recv_frame(s))
```

# DNASST02 — блочный формат сегментов с кодами Рида–Соломона (v3.0)

## Зачем

DNASST01 хранит записи линейно с CRC32 на запись: повреждение детектируется,
но восстановить данные не из чего. DNASST02 делит сегмент на блоки 4 KiB и
кодирует их страйпами Рида–Соломона GF(2^8): любой отказ до `m` шардов
(4 KiB-секторов) на страйп восстанавливается математически — по принципу
репарации ДНК.

## Геометрия

| Параметр | Значение по умолчанию | Настройка |
|---|---|---|
| Блок (шард) | 4 096 B | константа `BLOCK_SIZE` |
| Страйп | k данных + m parity | `--erasure-k 4 --erasure-m 2` |
| Поле | GF(2^8), полином 0x11D (крейт `reed-solomon-erasure`, матрица Коши) | — |
| CRC блока | CRC32C (SSE4.2) | в таблице CRC |
| Допустимые потери | ≤ m шардов на страйп (2 из 6 блоков = 33 %) | `m` |
| Накладные расходы места | +50 % при 4+2 | k/m |

## Раскладка файла (little-endian)

```
[суперблок      4096 B]  магия b"DNASST02", k, m, счётчики, CRC
[регион данных]          S_data  × (k+m) блоков — записи, упакованные подряд
[индекс-регион]          S_index × (k+m) блоков — блочный индекс key→(блок,смещ)
[таблица CRC, копия A]   (S_data+S_index)×(k+m) × u32
[таблица CRC, копия B]   — дубликат для отказоустойчивости метаданных
[футер          64 B]    перекрёстные копии геометрии + CRC таблицы + магия
```

Суперблок и футер несут идентичную геометрию: выход из строя любого из них
переживается за счёт второго. Индекс-регион защищён теми же страйпами RS.

## Записи

Формат записи идентичен DNASST01:
`[crc32 u32][klen u32][vlen u32][tombstone u8][key][val]`.
Записи упакованы непрерывно по логическим дата-блокам (страйп s владеет
блоками s·k … s·k+k−1); запись может пересекать блоки и страйпы.

## Интерливинг (damage-spread)

Физическая позиция шарда (страйп s, индекс idx) — `idx·S + rotate(s, seed)`,
где seed детерминированно выводится из имени файла. Соседние физические блоки
принадлежат РАЗНЫМ страйпам, parity перемешан с данными: последовательная
порча секторов бьёт по одному шарду страйпа, а не по нескольким.

## Репарация

1. **Детекция** — CRC32C каждого блока против таблицы CRC.
2. **Реконструкция** — при промахе CRC весь страйп перечитывается, недостающие
   шарды восстанавливаются из выживших (≥ k из k+m), блоки перезаписываются
   in place, повторно проверяются.
3. **Эскалация** — если повреждений в страйпе > m, движок поднимает копию
   сегмента со Стрэнда B (гомологичная рекомбинация).
4. **Карантин** — сегмент с непоправимым страйпом остаётся доступным: ключи
   затронутой зоны возвращают честную ошибку с локализацией
   `segment:stripe:shard`, остальной сегмент и БД продолжают работать.
5. **Журнал** — каждая бляшка пишется в `repair_journal.jsonl`.

## Миграция DNASST01 → DNASST02

Только ручная (приоритет — надёжность):

```bash
dna-db-core doctor --data-dir ./dna_data --migrate
```

Читает legacy-сегменты, перезаписывает в DNASST02 атомарно (.tmp → rename).
Записи с несовпадающим CRC переносятся без чуда — о них честно сообщается.

## Совместимость

- v2.1.0 НЕ читает DNASST02 (новая магия в футере).
- v3.0 читает оба формата; пишет только DNASST02.
- Chaos-тест: `scripts/chaos_test.py` — 100 000 ключей, порча секторов,
